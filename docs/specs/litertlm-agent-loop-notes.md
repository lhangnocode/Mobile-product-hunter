## Hard Conclusion

The previous failure should be treated as an agent-loop/message-role bug until proven otherwise.

LiteRT-LM has two valid tool-call modes:

1. Native automatic loop:
   - `ConversationConfig.automaticToolCalling = true`
   - LiteRT-LM executes registered tools internally.
   - LiteRT-LM sends tool results back to the model internally.
   - The app should display the final model answer.

2. Manual loop:
   - `ConversationConfig.automaticToolCalling = false`
   - The app receives `Message.toolCalls`.
   - The app executes tools.
   - The app sends the tool response back with `Message.tool(Contents.of(Content.ToolResponse(...)))`.

Anything else is invalid or risky. In particular, tool results must not be sent back as a normal user `Contents` message.

## Confirmed API Behavior

### Conversation and Streaming

LiteRT-LM creates an `Engine`, then a `Conversation` from `Engine.createConversation(config)`.

The Kotlin API exposes:

- `Conversation.sendMessage(contents, extraContext): Message`
- `Conversation.sendMessageAsync(contents, callback, extraContext)`
- `Conversation.sendMessageAsync(contents, extraContext): Flow<Message>`

The app currently uses the Flow API through `LlmRuntime.sendMessage(contents)`.

Important local AAR detail:

- `Conversation.sendMessage(Contents, extraContext)` wraps the contents as a user message.
- `Conversation.sendMessageAsync(Contents, ...)` also uses the contents overload.
- Therefore `Contents.of(Content.ToolResponse(...))` is not enough for manual tool calling.
- Manual tool results require the `Message` overload and `Message.tool(...)`.

### Tool Registration

The official Kotlin guide says tools are registered through `ConversationConfig.tools`.

Kotlin function tools should be implemented as:

- a class implementing `ToolSet`
- methods annotated with `@Tool`
- method parameters annotated with `@ToolParam`
- registered with `tool(MyToolSet())`

This app should keep using:

```kotlin
ConversationConfig(
    tools = listOf(tool(agentToolSet)),
    automaticToolCalling = true,
)
```

### Automatic Tool Calling

Official behavior:

- By default, tool calls generated by the model are automatically executed by LiteRT-LM.
- The tool execution results are automatically sent back to the model to generate the final response.
- Manual tool execution is only needed when `automaticToolCalling=false`.

Therefore, the normal expected loop is:

```text
user message
-> model emits tool call
-> LiteRT-LM executes registered Kotlin tool
-> LiteRT-LM sends tool result back into the same conversation
-> model emits final answer
```

The app should not need a custom direct-tool shortcut for normal automatic tool use.

### Manual Tool Calling Shape

When `automaticToolCalling=false`, the official Kotlin guide describes this manual flow:

```kotlin
val responseMessage = conversation.sendMessage("...")
if (responseMessage.toolCalls.isNotEmpty()) {
    val toolResponses = mutableListOf<Content.ToolResponse>()
    for (toolCall in responseMessage.toolCalls) {
        val toolResponseJson = executeTool(toolCall.name, toolCall.arguments)
        toolResponses.add(Content.ToolResponse(toolCall.name, toolResponseJson))
    }

    val toolResponseMessage = Message.tool(Contents.of(toolResponses))
    val finalMessage = conversation.sendMessage(toolResponseMessage)
}
```

Important details:

- Tool responses are represented by `Content.ToolResponse(name, response)`.
- Tool response messages are created with `Message.tool(Contents.of(toolResponses))`.
- The response is sent back as a `Message`, not as a normal user text message.
- `LlmRuntime` must expose a `Message` send path before the app can implement manual tool calling correctly.

## Local AAR Evidence

The decompiled `Conversation.sendMessage(...)` loop in `litertlm-android:0.12.0` shows:

- It sends the message JSON to native inference.
- If the returned JSON has `tool_calls`:
  - if `automaticToolCalling=false`, it returns a `Message` with `toolCalls`.
  - if `automaticToolCalling=true`, it calls an internal `handleToolCalls(...)`.
  - the internal result becomes the next message JSON and the loop continues.
- It repeats until the model returns `content`, or until a recurring tool-call limit is hit.

This matches the official guide: with automatic tool calling enabled, LiteRT-LM should already run an internal model-tool-model loop.

The decompiled `ToolKt.tool(ToolSet)` and `ExperimentalFlags` also show:

- `convertCamelToSnakeCaseInToolDescription` defaults to `true`.
- Kotlin tool method names are exposed to the model as snake_case tool names.
- For this app, `getProductDetail` is exposed as `get_product_detail`, `searchProducts` as `search_products`, and so on.
- Agent instructions must not tell the model to call camelCase names because that conflicts with the actual LiteRT tool schema.

The decompiled `JsonConvertersKt.toJsonElement(...)` shows:

- `Map`, `List`, primitives, and `JsonElement` become structured JSON.
- A Kotlin `String` return value becomes a JSON string primitive.
- Therefore app tools should return `JsonElement` or simple structured values, not a JSON-encoded `String`, when the model needs to read the tool result.

## Current App Problem

Observed runtime behavior:

- Logcat shows `buildConversationConfig tools=1 automaticToolCalling=true`.
- OkHttp logs show backend API calls are executed by the registered tool.
- The final model response still says it cannot access pricing or comparison data.

That means the likely failure is not "no tool registered" and not "no tool executed".

The likely failure is one of:

1. The app-level manual loop is not giving tool results back with the LiteRT-LM `tool` role.
2. The app is mixing automatic tool calling with a custom manual/planner loop.
3. The app's streaming wrapper is displaying a pre-tool or failed intermediate model message instead of the final post-tool response.
4. The Kotlin tool return value is too large/noisy for the model to use well.
5. The backend search result is broad and noisy, so the model degrades to an apology.

## Implementation Direction

Do not add a separate app-level direct-tool shortcut while `automaticToolCalling=true`.

Preferred fix order:

1. Remove the custom planner/direct-tool loop from `AgentOrchestrator`.
2. Keep `automaticToolCalling=true`.
3. Keep LiteRT-native `ToolSet` and `tool(agentToolSet)`.
4. Let LiteRT-LM perform the model -> tool -> model loop.
5. Make tool return payloads compact and model-friendly.
6. Keep tool result JSON small:
   - no giant full platform arrays
   - top 3 to 5 relevant results
   - include only product name, platform, current price, original price, discount, stock, URL
7. Use synchronous `Conversation.sendMessage(...)` in a diagnostic path if needed, because the local AAR clearly performs automatic tool recursion in the synchronous method.
8. Only use manual `Message.tool(...)` loop if `automaticToolCalling=false`.

If manual mode is chosen later, the required shape is:

```text
user Message
-> model Message with toolCalls
-> app executes matching tool(s)
-> Message.tool(Contents.of(Content.ToolResponse(toolName, resultJson)))
-> model final Message
```

The app must not do this:

```text
user Message
-> model/planner asks for a tool
-> app executes tool
-> sendMessage(Contents.of(Content.ToolResponse(...)))
```

That second flow sends the tool result through the user-message overload and does not match the official manual tool-calling contract.
